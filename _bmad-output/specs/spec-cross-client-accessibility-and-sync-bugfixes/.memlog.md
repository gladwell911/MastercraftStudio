updated: 2026-09-02T12:02

- (direction) 用户提供 16 条手机端与电脑端缺陷，并要求先生成 bmad-spec，再执行 Story Breakdown。
- (decision) 规格工作区采用 mc/_bmad-output/specs/spec-cross-client-accessibility-and-sync-bugfixes；该工作区统一承载 mc 桌面端与 rc 手机端的跨项目修复合同。
- (capability) CAP-1：手机用户启动传输到手机、打开文件或下载文件后，应先立即进入对应进度界面，再在该界面看到准备文件、连接电脑端、等待接收、下载中、失败或完成等实时状态。
- (capability) CAP-2：手机传输界面应提供一个暂停/继续切换按钮和一个停止按钮；按钮在所有状态均保持可聚焦可点击，当前动作不适用时点击不产生状态变化。
- (capability) CAP-3：手机设置应提供推送通知开关；开启时正常呈现电脑端回复通知，关闭时不呈现此类推送通知。
- (capability) CAP-4：手机菜单显示的当前模型应与电脑端实际选定模型一致，不得固定显示 codex。
- (capability) CAP-5：打开提取文件后再次进入相关流程时应返回聊天详情；桌面回答详情点击继续后也应返回聊天详情，避免残留在临时详情页。
- (capability) CAP-6：手机删除聊天后，删除结果应在页面刷新、从其他页面返回和应用重启后保持，不得因缓存或同步回写重新出现。
- (capability) CAP-7：手机文件标签中的每条记录只显示文件名和当前状态，状态覆盖已完成、正在下载、下载失败、等待接收及其他实际传输状态。
- (capability) CAP-8：桌面端焦点位于笔记列表、历史聊天列表、回答列表或模型选择组合框时，按一次空格应执行与 Alt+D 相同的输入框聚焦行为。
- (capability) CAP-9：手机命令按钮中的命令被点击时应触发系统标准点击音效。
- (capability) CAP-10：手机笔记详情默认进入文字输入模式，底部显示编辑框，左下角提供切换到语音输入的按钮。
- (capability) CAP-11：手机笔记详情保留多行文本的段落结构，并让屏幕阅读器可逐行获得独立焦点。
- (capability) CAP-12：手机回答详情底部按钮布局应与聊天详情一致，提取文件按钮位于右下角主按钮上方。
- (capability) CAP-13：聊天的回答列表和执行列表尾部不得显示来自先前回复的陈旧内容或重复内容。
- (constraint) 手机端实现位于 rc Flutter 项目，桌面端实现位于 mc wxPython 项目；涉及共享状态或协议的故事必须验证两端兼容。
- (constraint) 所有 UI 改动必须保持屏幕阅读器语义、可预测的键盘焦点和稳定导航，不能用禁用控件让暂停、继续或停止按钮从辅助技术中消失。
- (constraint) mc 后台轮询没有可见状态变化时不得调度 UI 线程、重绘列表、改变选择或焦点、写入应用状态。
- (constraint) 耗时文件准备、连接和下载不得阻塞首次页面导航；进度页必须先显示，异步工作随后更新可见状态。
- (constraint) 聊天删除必须以持久化与同步层的确定状态为准，不能由过期本地缓存、后台刷新或远端旧快照复活。
- (constraint) 每项 UI 修复都需运行对应的定向无障碍或 UI 自动化回归测试；跨端状态修复还需覆盖持久化、协议或模型工作流测试。
- (non-goal) 本次不重新设计整套手机导航、聊天协议、文件传输协议或桌面快捷键体系。
- (non-goal) 本次不改变聊天内容、文件内容或笔记内容本身，只修复呈现、交互、持久化与同步一致性。
- (assumption) 推送通知开关默认理解为只控制系统通知呈现，不阻止聊天数据在用户打开应用后正常同步。
- (assumption) 按钮在任何状态可用理解为始终可聚焦且不显示 disabled 语义；动作不适用时处理器安全无操作。
- (assumption) 立即进入界面理解为点击后的首个可渲染帧完成导航，耗时准备、连接或下载全部在目标界面启动。
- (question) 关闭推送通知时，是否仅禁止系统通知呈现，还是也要停止后台接收电脑端回复数据？
- (question) 首次安装或升级后，应用内推送通知开关的默认值应为开启还是关闭？
- (question) 文件状态文案是否已有必须复用的完整枚举，还是允许实现时补充准备中、连接中、已暂停、已停止等状态？
